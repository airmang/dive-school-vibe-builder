# Grill Me — 교사의 업무를 작은 앱으로 바꾸기

## 질문 운영

이미 대화/문서에 있는 답을 먼저 정리하고 비어 있는 부분만 질문한다.
질문을 시험처럼 내지 않는다. 기술 용어보다 실제 업무 장면을 묻는다.
한 번에 질문 한 개. 모호하면 한 번 더 구체적인 사례를 묻고 다음으로 넘어간다.
답변을 PROJECT 초안 또는 대화에 요약하되 실명/상담 원문은 기록하지 않는다.

## 기본 질문 흐름

| 순서 | 실제 질문 예 | 얻어야 할 결정 |
|---|---|---|
| 1 | 이 앱이 생기면 지금 하시는 일 중 무엇을 하지 않아도 되나요? | 문제와 최소 성공 조건 |
| 2 | 누가 입력하고 누가 보기만 하나요? | 사용자 역할과 쓰기 권한 |
| 3 | 처음 켠 사람이 가장 먼저 해야 할 행동은 무엇인가요? | 핵심 화면과 사용 흐름 |
| 4 | 종이에 한 건을 적는다면 어떤 칸이 꼭 필요한가요? | 최소 데이터 필드 |
| 5 | 반 학생끼리 서로의 자료를 봐도 되나요? 외부인은요? | 공개/본인/담당자 범위 |
| 6 | 이번에는 없어도 괜찮은 기능은 무엇인가요? | 제외 범위와 과잉 개발 방지 |
| 7 | 앱이 제대로 됐다고 판단할 장면 세 가지는 무엇인가요? | 수용 테스트 |
| 8 | 링크를 받은 뒤 누가 관리하고 언제 자료를 지우나요? | 실제 운영 책임 |

한 질문에 모든 세부항목을 묶어 설문지를 만들지 않는다. 로그인·권한 선택은 구체적 사례로 묻는다.
계정/요금/기기 설치는 먼저 사람이 선택해야 할 때만 질문한다. 정해진 스택을 다시 비교시키지 않는다.

## 좋은 질문의 예

“학급 일정이라고 하셨는데 공개 범위를 하나만 정하겠습니다.
① 링크를 아는 누구나 공통 일정 조회 ② 승인된 학생만 조회.
학생 이름이나 개인별 일정이 없다면 ①이 더 단순합니다. 어느 범위가 맞나요?”

“학생이 상담카드를 작성한다고 하셨습니다. 선생님의 추가 메모도 학생에게 보여야 하나요,
아니면 학생 작성란과 교사 비공개 메모를 분리해야 하나요?”

## 나쁜 질문

- 어떤 상태 관리 라이브러리를 쓸까요? → 교사가 결정할 업무 요구가 아님.
- 15개 항목을 전부 답해 주세요. → 첫 앱 전에 피로를 늘림.
- 로그인은 나중에 생각하죠. → 구현 순서는 나중이어도 권한 설계는 처음에 필요.
- 개인정보는 없죠? → 이름 없이도 학생과 연결되는 진학 일정이 있을 수 있음.

## 종료와 승인

다음 형식으로 짧게 합의안을 보여준다.

```text
목적: 교사가 등록한 공통 학급 일정을 학생이 확인
교사: 일정 등록/수정/삭제
학생: 승인된 범위의 일정 조회
데이터: 제목, 날짜, 종류, 설명
이번 기능: 등록, 목록, 수정/삭제, 로그인
제외: 알림, 채팅, 파일, 자동 크롤링
보안: 가상 데이터로 제작, 개인별 진학/상담 자료 제외
완료 장면: 다른 기기에서 확인 + 학생 쓰기 차단 + 모바일 사용
확인할 것: 공개 열람 여부
```

“이 범위로 시작해”가 확인되면 세 문서를 생성·구체화하고 P0 검증 기록에 실제 승인 사실을 남긴다.
시간을 줄여 달라는 요청에는 미확정 사항을 표시한 안전한 초안으로 로컬 작업부터 진행한다.
