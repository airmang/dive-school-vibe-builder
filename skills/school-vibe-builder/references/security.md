# 학교 앱 보안·실운영 게이트

이 문서는 구현 체크리스트다. 법률 검토, 보안 감사, 학교의 사용 승인을 대신하지 않는다.
기술적으로 되는 것과 학교에서 실제 학생 데이터를 저장해도 되는 것은 별개다.
근거 문서: [공식 출처](sources.md) S3~S9.

## 데이터 분류와 최소화

공개 공지, 학급 내부 자료, 학생 본인 자료, 교사 비공개 자료를 구분한다.
처음에는 가상 데이터만 쓴다. 운영 때 필요한 수집 항목·안내·보관/삭제·위탁/저장 위치 등을 학교 절차에 따라 확인한다.
개별 진학 정보나 상담 내용은 단순히 이름을 지웠다고 공개 자료가 되지 않는다.
테스트용 로그·스크린샷·Git 이슈에도 학생 자료를 복사하지 않는다.

## 접근 제어

Supabase의 브라우저용 publishable key는 사용자 권한을 부여하는 비밀키가 아니다. Auth와 DB 권한/RLS가 필요하다.
노출 테이블을 만들 때 RLS와 grants를 함께 설정하고, 필요한 작업만 허용한다.
UPDATE는 기존 행 접근 조건과 새 값 조건을 모두 검토한다. teacher_id/student_id 바꿔치기를 시험한다.
INSERT에서 소유자 ID를 임의 지정할 수 없게 한다. 담당 교사 자격은 별도로 검증한다.
`user_metadata`의 역할, 화면에 표시된 이름, 이메일 문자열, 숨겨진 버튼을 신뢰 경계로 삼지 않는다.
역할·학급 관계는 사용자에게 수정 권한이 없는 테이블/서버 관리 메타데이터로 유지한다.
행을 읽게 한 뒤 특정 메모 열만 화면에서 숨기지 않는다. 분리 테이블/컬럼 권한 등으로 실제 차단한다.
뷰, RPC, Storage, 내보내기 API를 추가하면 그 경로도 독립적으로 점검한다. 불필요하면 MVP에 넣지 않는다.
서버에서 세션을 쓴다고 인증이 자동 완성되는 것은 아니다. 현재 공식 SDK 방식으로 토큰/사용자를 검증한다.
개인별 응답이나 인증 쿠키가 공용 캐시로 공유되지 않도록 확인한다.

## 반드시 실행할 허용·거부 시험

테스트는 가상 데이터와 승인된 테스트 계정으로만 한다. 토큰을 PLAN에 적지 않는다.
A=소유자/담당자, B=다른 사용자, C=비구성원, anonymous=비로그인으로 구분한다.

| 동작 | 기대 결과 |
|---|---|
| 담당 교사 자신의 허용된 일정 등록/수정/삭제 | 성공·실제 DB 반영 |
| 학생의 허용된 조회 | 올바른 행/필드만 반환 |
| 학생이 teacher 역할이나 소유자 ID를 변경 | 거부·원 데이터 불변 |
| B가 A의 학생 자료 row ID로 조회 | 해당 자료 미반환 |
| B가 A의 row 수정/삭제 | 거부 또는 0건·원 데이터 불변 |
| 비구성원이 가입/로그인 후 데이터 조회 | 거부 |
| 비로그인 개인 자료/API 접근 | 거부 |
| 승인된 공개 일정 조회 | 승인된 공개 자료만 반환 |
| 검색·CSV·직접 API로 같은 우회 시도 | 같은 정책 유지 |

`service_role`/관리자 SQL로 시험한 성공은 RLS 시험이 아니다.
거부는 오류 응답일 수도 있고 빈 행/0건 갱신일 수도 있다. HTTP 200 여부만 보지 말고 원 자료를 확인한다.
가급적 반복 가능한 테스트를 저장한다. 도구가 없으면 실제 사용자 세션으로 수행하고 수동 확인 근거를 기록한다.

## 비밀과 환경

브라우저에는 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`만 제공한다.
secret/service-role, DB 비밀번호, OAuth client secret은 서버/서비스 설정 외부로 노출하지 않는다.
기본 MVP에는 관리자 키를 쓰는 런타임 기능을 넣지 않는다. 꼭 필요하면 서버 전용이며 별도 검토한다.
`.env.example`은 빈 값만. `.env.local`은 Git 제외. ignore 추가로 이미 추적된 비밀이 사라지지 않는다.
유출되면 파일 삭제뿐 아니라 키 폐기/재발급과 이력·접근 내역 검토가 필요하다.
다른 교사의 프로젝트 연결 정보를 복사하지 않는다. 사용자에게 본인 프로젝트와 키 종류를 확인시킨다.

## 외부 실행과 공개

테스트 DB라도 원격 변경 대상을 확인한다. 삭제·초기화·권한 확대는 사전 설명과 승인이 필요하다.
도구 권한 부족을 해결하려고 RLS/샌드박스/승인 절차를 끄지 않는다.
푸시와 배포는 단순 저장이 아닐 수 있다. 연결된 production 브랜치의 자동 배포 영향을 알려준다.
Vercel Preview와 Production 환경을 나누고 운영 리다이렉트 URL을 검증한다.
링크를 모른다는 것은 접근 제어가 아니다. 개인정보 앱은 비구성원 직접 접근도 거부해야 한다.

## 마지막 운영 질문

누가 계정을 소유하고 퇴직·담임 변경 때 어떻게 인계하는가?
자료 보관/삭제 시점과 수동 백업·복구 절차가 있는가?
현재 무료/유료 플랜 한도, 중단/일시정지, 메일 발송 제한, 서비스 약관을 확인했는가?
장애 시 대체 안내 방법이 있는가? 실제 학생 데이터 사용을 학교가 검토했는가?
연수 시연에서는 이 답이 없으면 가상 데이터 파일럿까지만 진행한다.
