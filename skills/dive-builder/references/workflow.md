# 공통 개발 흐름

## 일반 프로젝트

목표 구체화 → 첫 동작 단위 → 관련 검증 → 사용해 보기 → 개선/완료.
화면·DB·로그인·배포는 목표가 필요로 할 때만 추가한다. 기존 코드는 유지하고 최소 diff로 시작한다.
계획은 사용자가 체감할 수 있는 작은 결과 단위로 나눈다. 작업 제목 옆에 완료 기준과 시험 방법을 구체화한다.
일반 모드의 T1.1~T4.1은 초안 예시다. 해당 작업의 ID·개수·순서는 프로젝트에 맞춰 바꿔도 된다.
모든 항목을 적용 제외로 만드는 식으로 완료를 주장하지 않는다.

## 실행 환경과 첫 실행

작업 폴더, OS, 사용 중인 런타임, 프로젝트 설정과 실제 오류부터 확인한다.
패키지·버전·계정이 필요하면 공식 자료와 설치된 환경을 확인한다. 최신이라는 이유로 기존 프로젝트를 업그레이드하지 않는다.
실행하지 못한 명령은 시도/차단으로 남긴다. 사용자가 해야 할 조작과 성공 화면을 설명한다.

## 오류 처리

관찰한 증상 → 재현 → 가설 하나 → 작은 수정 → 같은 사례 재시험.
같은 실패 2회 반복 시 재시도 전에 가설·로그·최근 변경·권한/환경을 다시 대조한다.
에러를 숨기거나 테스트를 삭제해서 통과시키지 않는다. 원격 장애와 로컬 코드 오류를 구분한다.

## 중단·재개·되돌리기

PLAN에 현재 작업, 마지막 명령과 결과, 실패/보류, 다음 행동, 실행 방법, 복구 지점을 기록한다.
새 세션에서는 코드·Git diff·실행 상태를 다시 확인한다. localhost 주소가 기록되어 있다고 서버가 켜져 있는 것은 아니다.
되돌리기 전 영향받는 파일과 사용자 변경을 보여준다. 체크포인트 생성도 대상 파일을 점검한 뒤 한다.
reset --hard, clean -fd, 무조건적인 stash/force push는 기본 절차가 아니다.

## 모드 변경·구버전 이관

기존 PROJECT/PLAN/AGENTS를 덮어쓰거나 새 init으로 갈아엎지 않는다.
1. 현재 파일을 읽고 사용자 변경·완료 근거를 보존한다. 필요하면 별도 로컬 백업을 합의한다.
2. 요구사항 변화와 추가/대체할 작업을 설명한다.
3. 사용자가 선택한 모드에 맞춰 PLAN의 DIVE_MODE와 관련 작업을 편집한다.
4. webapp으로 바꾸면 해당 스킬의 PLAN/필수 작업을 기존 PLAN에 병합한다. 기존 ID가 겹치면 이력을 남기고 명시적으로 매핑한다.
5. webapp에서 general로 바뀌더라도 기존 데이터의 보안 의무가 사라지지 않는다. 해제·이관·남은 운영 위험을 기록한다.
6. 바뀐 기능의 기존 검증을 다시 연다. 문서 전환만으로 재검증 완료를 인정하지 않는다.

v0.1 PLAN에는 DIVE_MODE 등 설정이 없다. status는 legacy-or-unknown으로 읽지만 check는 전환 안내와 함께 차단한다.
웹앱을 유지한다면 DIVE_MODE: webapp, 저장/인증 필요 값, 실제 계획 합의 상태를 헤더에 추가한다.
기존 PASS/MANUAL-PASS 기록은 보존하되 최신 구현에 여전히 유효한지 확인한다.

## 판단 범위

도우미 스크립트는 문서 형식과 일부 정적 패턴만 검사한다. 승인/근거는 사람이 편집할 수 있으므로 위조 방지 장치가 아니다.
코드 변경과 근거를 암호학적으로 연결하지 않는다. 실제 검증 무효화 판단은 에이전트가 diff·테스트로 수행해야 한다.
일반 모드에서 작업을 삭제했다고 자동 탐지하지 않는다. 계획 변경 기록과 diff를 함께 검토한다.
