# 요구사항을 개발 계획으로 바꾸는 인터뷰

Grill Me는 퀴즈나 심문이 아니다. 잘못 만들지 않도록 중요한 빈칸을 찾는 대화다.
이미 알려진 것을 먼저 요약한다. 한 번에 질문 하나, 필요하면 2~3개의 쉬운 선택지와 추천을 제시한다.
질문 수를 채우지 않는다. 사용자가 충분히 설명했다면 바로 합의안으로 넘어간다.

## 필요한 정보

누가 무엇을 하려는지, 지금 반복하는 일과 불편, 입력과 기대 출력, 실행할 기기,
혼자 쓰는지 다른 사람과 공유하는지, 보존할 원본과 민감정보, 첫 버전의 완료 기준을 파악한다.
기술 이름보다 사용 방식으로 묻는다. 계정/비용/공개 범위는 실제로 필요할 때 확인한다.
기존 코드·파일이 있으면 먼저 읽고 새로 만드는 게 맞는지 판단한다.

## 예시

파일 합치기: “표 안의 값만 합치면 되나요, 원래 셀 서식도 유지해야 하나요?”
신청 앱: “신청자는 자기 신청만 보나요, 전체 신청 현황을 봐도 되나요?”
게임: “첫 버전에서 플레이어가 할 핵심 행동은 무엇인가요?”
봇: “메시지를 작성만 할까요, 실제 채널에 보내야 하나요?”

사용자가 기술을 모른다면 최소 구성 1개를 추천하고 이유·한계를 설명한다.
선택한 프로젝트 종류로 기능을 금지하지 않는다. 게임+API, 분석+웹화면 같은 조합도 허용한다.

## 합의안

목표, 첫 버전에서 할 행동, 나중으로 미룰 것, 입력/출력과 접근 범위, 실제 확인 가능한 완료 기준,
추천 구현 방법을 짧게 제시한다. 개발 시작 요청 자체에 충분한 범위 승인이 있으면 확인을 반복하지 않는다.
실제 공개·원본 파괴 등 별도 위험 결정은 분리한다. 사용자가 질문만 요청했으면 코드 구현을 하지 않는다.
