# 공유 웹앱 구현·연결·배포 가이드

이 문서는 계획을 대체하지 않는다. 이미 답한 내용을 다시 묻지 않는다. 현재 필요한 단계만 읽는다.

## 1~2. 첫 화면과 실행

프로젝트 폴더·설치된 Node·패키지 설정부터 확인한다. 기존 프로젝트이면 스택과 명령을 보존한다.
새 앱은 현재 공식 요구사항에 맞는 최소 구성으로 만든다. 한 화면·핵심 행동부터, 가상 데이터로 시작한다.
로컬 URL을 알려주고 사용자가 수행할 행동과 정상 결과를 안내한다. 빈 화면·오류 메시지·작은 화면도 확인한다.
코드 작성, 빌드 통과, 브라우저 동작은 서로 다른 증거다.

## 3. Supabase 준비

먼저 저장이 필요한지 확인한다. 필요 없다면 계정을 만들게 하지 말고 PLAN에 이유를 기록한다.
필요할 때: 사용자가 본인 계정으로 로그인 → 올바른 조직/프로젝트와 비용·리전을 확인 → 테스트용 프로젝트를 준비한다.
정확한 화면 위치는 최신 문서/사용자 화면으로 확인한다. 추측한 메뉴명을 단정하지 않는다.
에이전트는 테이블·제약·RLS·최소 grants를 포함한 SQL 마이그레이션을 파일로 만든다.
사람에게 SQL Editor에서 **검토한 SQL**을 적용하도록 안내하거나 승인된 연결 도구로 실행한다.
정상 결과는 “테이블이 보임”만이 아니라 일반 사용자에게 허용/차단이 맞는지 확인할 준비가 된 상태다.
오류 시 비밀값을 뺀 오류 코드/문구와 실행한 마이그레이션을 확인한다. RLS를 꺼서 해결하지 않는다.

## 4. 저장 연결

프로젝트 URL과 publishable key의 역할을 설명한다. .env.example에는 변수 이름과 빈 값만 둔다.
실제 값은 제외된 로컬 설정/배포 설정에 입력하며, 기존 파일을 덮어쓰거나 내용을 대화에 출력하지 않는다.
필요한 변수 이름의 예시는 assets/env-example.txt에 있다. 이 파일을 넣는다고 연결이 되는 것은 아니다.
환경변수 변경 후 필요한 재실행을 안내하고, 제한된 계정·가상 데이터로 저장→새로고침→다른 세션을 확인한다.
연결 실패는 환경값 누락/잘못된 프로젝트, 테이블 오류, 인증 실패, 권한 거부, 네트워크 오류로 나눠 확인한다.

## 5. 로그인·권한

필요한 인증 방식은 사용자 계정 정책에 맞춘다. 특정 학교 이메일과 교사 역할은 별개다.
등록/로그인/로그아웃/재접속을 실제 시험한다. 역할을 자기 손으로 바꾸거나 타인 데이터를 조회/수정할 수 없어야 한다.
권한은 DB/API에서 강제한다. 버튼 숨기기만으로 끝내지 않는다. 비공개 내용과 공개 데이터를 분리한다.
서로 다른 일반 사용자 A/B와 비로그인으로 허용과 거부를 시험하고 근거를 남긴다.

## 6. GitHub

원격 저장소·소유자·브랜치·공개 범위·자동 배포 영향을 확인한다.
prepush 도우미 + 실제 diff로 .env/개인정보/키/덤프를 확인한다. .gitignore만 추가해도 이미 추적된 파일은 사라지지 않는다.
승인된 파일만 커밋/업로드한다. 기존 배포 브랜치의 push는 실제 서비스에 영향을 줄 수 있다.
실패 시 인증/권한/브랜치 보호/네트워크 문제를 구분한다. 강제 push나 토큰 노출로 우회하지 않는다.

## 7. Vercel

사용자가 로그인하고 올바른 GitHub 저장소를 선택한다. 루트 폴더·빌드 명령·환경을 확인한다.
Preview와 Production 설정을 구분한다. 비밀값은 해당 환경의 설정에 넣고 공개 접두사 변수에 넣지 않는다.
환경변수 변경은 이전 배포를 바꾸지 않으므로 필요한 새 배포를 실행한다.
Supabase 인증을 쓴다면 실제 배포 주소에 맞는 Site URL/Redirect URLs와 제공자 콜백을 확인한다.
승인된 배포 후 실제 URL에서 핵심 동작을 시험한다. 빌드 통과와 로그인/저장 성공을 같은 것으로 기록하지 않는다.
오류 시 Build Log, 런타임 오류, 환경변수 이름/설정 유무, 리다이렉트 경로를 구분해 확인한다. 값은 숨긴다.

## 8. 공유·운영

다른 기기/별도 브라우저로 접근하고, 인증이 있다면 허용/비허용 사용자로 확인한다.
가상 데이터인지 실데이터인지, 누가 운영하는지, 비용·보관·백업·복구·중단 시 안내를 결정한다.
배포됐다는 이유만으로 실제 학생에게 공유하지 않는다. 정해진 대상에 대한 구체적인 공유 승인을 받는다.
S8.4의 공유 자체는 실제로 이루어진 뒤에만 완료로 기록한다.

## 웹앱+다른 기능

게임·파일 변환·외부 API·봇 기능도 목표에 맞으면 추가할 수 있다. 이 경로는 프로젝트 종류를 제한하지 않는다.
클라우드에 오래 실행되는 작업이나 로컬 장치 접근이 필요하다면 제약을 먼저 확인하고 대안을 제안한다.
