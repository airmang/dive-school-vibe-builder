# 선택적 학교 업무 출발 예시

프로필은 출발안이지 완성 요구사항이 아니다. `assets/profiles/*.json`은 초기 문서 생성에만 사용한다.
학급·교사 실명은 기본값으로 넣지 않는다. 교사마다 자기 프로젝트 폴더/저장소를 사용한다.

## calendar — 학급 일정 공유

핵심: 교사 등록 → 학생 조회. 처음에는 날짜순 목록과 월 선택만 만든다.
월간 격자 달력은 필요할 때 추가한다. 학생별 진학 일정과 섞지 않는다.
`owner_id`가 있다고 모든 로그인 사용자에게 교사 권한을 주지 않는다. 승인된 교사임을 별도로 확인한다.
단일 학급 MVP에는 다학교 조직/테넌트 관리 UI를 만들지 않는다.
공개 모드를 고르면 공개해도 되는 일정만 별도 범위로 제공하고 관리 기능은 계속 보호한다.

시작 질문: “모든 일정은 공통 공지인가요? 학생 이름이 붙는 개인 일정도 있나요?”
검증: 학생이 SELECT는 가능하되 INSERT/UPDATE/DELETE는 불가능해야 한다.
날짜만 있는 값은 `YYYY-MM-DD`를 일관되게 처리한다. UTC 자정 변환으로 날짜가 바뀌지 않게 시험한다.

## admissions — 면접·실기·논술 일정

핵심: 학생은 본인 일정, 교사는 담당 학생 일정. 입력 주체는 인터뷰에서 정한다.
학생 A의 지원 대학/전형을 학생 B에게 목록·검색·내보내기로 노출하지 않는다.
학번/이름을 입력했다고 본인이라고 인증하지 않는다. 승인된 auth 사용자와 연결한다.
대학 공통 시험 날짜와 개인별 지원 정보는 다른 공개 수준이다. 필요하면 분리한다.
날짜 미확정/시간 미정/장소 추후 공지를 실제 확정값으로 채우지 않는다.
D-day는 서울 기준 날짜 차이로 계산하고 당일은 D-day, 지난 날짜는 경과 표시로 구분한다.
충돌 경고는 날짜/시간이 불완전하면 '겹칠 수 있음' 수준으로 표시한다.
자동 웹 수집은 MVP 밖. 정확한 일정 확인은 학교/대학 공식 안내와 사람이 대조한다.

시작 질문: “학생이 자기 일정을 직접 입력하나요, 선생님이 전부 입력하나요?”
예시 데이터: `학생 A(가상)`, `가온대학교(가상)` 등을 사용한다. 실제 대학의 가짜 입시 날짜를 만들지 않는다.
검증: student A → student B의 row ID로 직접 API 요청해도 조회·수정 불가.

## counseling — 상담카드

핵심: 담당 교사의 기록 작성·검색. 학생 작성 요구가 있으면 제출란과 교사 메모를 분리한다.
'수시'의 의미를 확인하고 입시 상담이면 생활·건강·가정 정보 필드를 자동으로 추가하지 않는다.
학생에게 행 SELECT 권한을 주고 교사 메모만 화면에서 가리는 설계는 피한다.
처음부터 파일 첨부·녹음·상담 내용 AI 분석을 추가하지 않는다.
비공개 상담 자료는 실운영 검토가 끝나기 전까지 가상 데이터만 쓴다.
다른 교사의 접근도 기본 거부한다. 인계가 필요하면 별도 승인 절차로 범위를 확정한다.

시작 질문: “학생이 직접 작성할 부분과 선생님만 볼 부분이 각각 있나요?”
검증: 다른 교사, 학생, 비구성원의 모든 조회/수정/내보내기 경로가 차단되어야 한다.

## custom — 자유로운 웹앱

다루는 입력·출력·저장·접근 범위를 확인한다. 학교 업무일 필요는 없다.
기자재 대여/신청 관리도 담당자·본인·외부인의 권한을 구분한다.
공통 템플릿에 맞지 않는다는 이유로 업무를 억지로 캘린더 모양으로 만들지 않는다.
